# Автокоммит завершённых задач AI Anki

Пользователь установил постоянное правило для этого проекта: после каждой
выполненной задачи создавать локальный коммит. Применяй навык без отдельного
вызова и без повторного подтверждения коммита. Явное указание пользователя
«не коммитить» или «только подготовить изменения» имеет приоритет.

## Граница задачи

- В начале работы посмотри `git status --short --branch` и состав индекса,
  чтобы отличать изменения задачи от уже существующих правок.
- Коммит — часть завершения задачи, перед финальным ответом. Промежуточные
  сообщения, чтение файлов и отдельные вызовы инструментов не требуют коммитов.
- Если задача не изменила файлы репозитория, не создавай пустой коммит.
- Один законченный набор изменений — один логический коммит вместе с его
  тестами и документацией. Независимые изменения разделяй по смыслу.

## Проверка и фиксация

1. Закончи реализацию и проверь её подходящим способом: целевые тесты для
   логики, сборка для изменений интерфейса, проверка генерации для контента,
   чтение и проверка ссылок для инструкций. Не повторяй уже успешные проверки,
   если код после них не менялся. Исправь обнаруженные ошибки; ограничения
   среды опиши честно, не называя невыполненные проверки успешными.
2. Проверь `git diff --check`, список файлов и относящийся к задаче diff.
   Не включай секреты, временные данные, скачанные материалы и результаты
   сборки. Каталоги `.agents/` и `.claude/` могут содержать импортированные
   навыки: добавляй только конкретные файлы текущей задачи, а не весь каталог.
3. Добавь в индекс явные пути через `git add -- <paths>`. Проверь
   `git diff --cached --check` и окончательный состав коммита. Не используй
   без разбора `git add .` или `git add -A`.
4. Сохрани посторонние изменения и ранее подготовленный индекс. Если в нём
   есть чужие файлы, исключи их из своего коммита, например через
   `git commit --only -- <paths>` для непересекающихся файлов. При смешанных
   правках одного файла подготовь только относящиеся к задаче фрагменты;
   не сбрасывай чужую работу ради чистого статуса.
5. Создай коммит в текущей ветке с сообщением Conventional Commits:
   `feat(scope): ...`, `fix(scope): ...`, `docs(scope): ...` или `chore(scope): ...`.
   Следуй языку истории проекта: короткий английский заголовок в повелительной
   форме; при необходимости поясни причину изменения и проверку в теле.
   Многострочное сообщение передавай через файл и `git commit -F`, учитывая
   PowerShell. Не изменяй глобальные настройки Git ради коммита.
6. Проверь результат через `git log -1 --oneline` и `git status --short`.
   Если коммит не создался, исправь устранимую причину и повтори; не обходи
   hooks и ограничения разрешений. При внешней блокировке явно сообщи,
   что осталось несохранённым, вместо заявления о полном завершении.

Не выполняй push, amend, rebase или переписывание истории без отдельного
указания пользователя. Правило разрешает локальный коммит завершённой задачи,
а не публикацию изменений или фиксацию посторонней работы.

В финальном ответе кратко укажи результат задачи, выполненные проверки и хеш
созданного коммита. Если изменений для коммита нет, сообщи об этом без пустого
коммита. Не заканчивай задачу предложением «могу закоммитить» — выполни коммит.
